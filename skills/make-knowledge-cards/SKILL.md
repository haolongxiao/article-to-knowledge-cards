# Make Knowledge Cards

把文章或本地 Markdown/TXT 文件转换成 5~8 张高质量知识卡片，帮助用户高效记忆和理解。

---

## 何时使用本 Skill

当用户满足以下任一条件时，调用本 Skill：

- 用户粘贴了一段文章、博客、笔记或技术文档
- 用户提供了本地 `.md` 或 `.txt` 文件
- 用户明确要求生成知识卡片、总结卡片、记忆卡片

---

## 输入来源

| 支持 | 不支持 |
|------|--------|
| 用户直接粘贴的纯文本 | 网页 URL / 在线抓取 |
| 本地 `.md` 文件 | PDF 文件 |
| 本地 `.txt` 文件 | Anki 导入格式 |
| | 图形界面操作 |

如果用户提供了不支持的输入类型，礼貌说明并请用户改用支持的格式。

---

## 核心规则（必须严格遵守）

1. **一张卡片 = 一个知识点**。每张卡片只讲一件事，不要把多个概念塞进一张卡。
2. **只提取真正重要的内容**。跳过寒暄、广告、重复段落、"你好世界"之类的模板文字。
3. **删除重复**。原文多次提到的同一件事，只在一张卡片中讲清楚。
4. **不能编造**。所有信息必须来自原文，不得添加原文没有的事实、数据或结论。
5. **信息不足时不要硬凑**。短文（200 字以下）可能只够 2~3 张，就做 2~3 张；中等长度（300~800 字）通常 4~6 张；长文（1000 字以上）可以 6~8 张。**宁可数量少，不要稀释内容质量**。
6. **合并次要知识点**。原文中相对次要的点（如"客户端-服务器架构"和"分层系统"都是 REST 的原则），如果单独拿出来太单薄，可以合并在一张卡片中。

## 卡片格式

每张卡片使用以下 Markdown 结构：

```markdown
### 📌 卡片 N — {标题}

| 字段 | 内容 |
|------|------|
| **核心知识** | 一句话概括最重要的结论或定义 |
| **简明解释** | 1~3 句话展开说明，让读者真正理解 |
| **例子 / 自测** | 一个具体例子，或一道帮助记忆的自测题 |
```

### 各字段要求

| 字段 | 要求 |
|------|------|
| **标题** | 简洁，8~20 字，点明具体知识点。❌ "原则一"、"基本概念"这种笼统标题；✅ "无状态通信的含义"、"REST 的五个设计原则" |
| **核心知识** | 必须是一句完整的话，是整个卡片的"TL;DR" |
| **简明解释** | 用自己的话重述原文，不要大段复制；控制在 50~150 字 |
| **例子 / 自测** | 二选一：原文有好例子就用例子，没有就出自测题（附答案）。**不要同时放例子和自测** |

### 自测题示例

- **填空题**："HTTP 状态码 404 表示 ____。" （答案：请求的资源不存在）
- **判断题**："TCP 是无连接的协议。" （答案：✗，TCP 是面向连接的）
- **联想题**：提到"哈希表冲突"，你会想到哪几种解决方式？（答案链地址法、开放寻址法、再哈希法等）

## 工作流程

### 第一步：读取输入

- 如果用户粘贴了文本，直接使用。
- 如果用户给出文件路径，先读取文件内容（仅支持 `.md` / `.txt`）。

### 第二步：理解原文

在生成卡片之前，先在内心完成以下思考：
1. 这篇文章的主题是什么？
2. 作者讲了哪几个关键概念或观点？
3. 哪些是背景信息，哪些是核心内容？
4. 各个概念之间是并列关系还是递进关系？

### 第三步：筛选知识点

按照以下优先级挑选知识点：
- ✅ 文中给出明确定义的概念
- ✅ 作者强调或加粗的要点
- ✅ 有具体数字、数据、对比的内容
- ✅ 容易混淆或记错的细节
- ✅ 有因果或步骤关系的流程

淘汰：
- ❌ 开篇问候、致谢、订阅提醒
- ❌ 原文只是换词重复的段落
- ❌ 没有实质内容的过渡句

### 第四步：生成卡片

按照卡片格式逐张输出。确保：
- 卡片之间互不重复
- 卡片顺序符合原文逻辑（从基础到进阶，从定义到应用）
- 每张卡片独立可读，不需要上下文

### 第五步：自检

输出完成后，回头检查：
- **真实性**：有没有哪张卡片包含了原文没有的信息？（有则删除或修改）
- **去重**：有没有哪两张卡片讲的是同一件事？（合并或删掉一张）
- **数量**：数量是否与原文长度匹配？不要为了凑数硬加。
- **核心知识质量**：每张卡片的"核心知识"是否真的抓住了要点？是不是一句话就能概括？
- **标题具体性**：有没有"原则一"、"基本概念"这种笼统标题？改成具体的知识点名称。
- **例子/自测单一性**：有没有同一张卡片里同时放了例子和自测题？二选一。

## 输出示例

假设输入是一篇关于 HTTP 状态码的短文：

```markdown
### 📌 卡片 1 — HTTP 状态码的分类

| 字段 | 内容 |
|------|------|
| **核心知识** | HTTP 状态码分为 5 类，首位数字代表类别。 |
| **简明解释** | 1xx 是信息提示，2xx 表示成功，3xx 表示重定向，4xx 表示客户端错误，5xx 表示服务器错误。 |
| **例子 / 自测** | 列出一个你在开发中常见的 4xx 错误码。（答案：404、403、401 等） |

### 📌 卡片 2 — 200 与 204 的区别

| 字段 | 内容 |
|------|------|
| **核心知识** | 200 OK 返回正常响应体，204 No Content 成功但不返回任何内容。 |
| **简明解释** | 两者都表示请求成功，但 204 常用于 DELETE 或某些 PUT 操作，表示"删完了，没东西给你看"。 |
| **例子 / 自测** | 判断题：GET 请求通常返回 204。（答案：✗，GET 应该返回 200 加响应体） |

### 📌 卡片 3 — 301 与 302 的区别

| 字段 | 内容 |
|------|------|
| **核心知识** | 301 是永久重定向，浏览器会缓存；302 是临时重定向，每次仍访问原地址。 |
| **简明解释** | 搜索引擎会把 301 的权重转移到新地址，302 则不会。做 URL 规范化时应该用 301。 |
| **例子 / 自测** | 把 `example.com` 永久跳转到 `www.example.com`，应该用哪个状态码？（答案：301） |
```

---

## 语言要求

- 与用户输入使用**相同语言**。中文文章输出中文卡片，英文文章输出英文卡片。
- 标题和字段名保持与示例一致（例如始终写"核心知识"而非"Key Point"）。

---

## 禁止事项

- 不要输出任何额外的前言或结语（例如"好的，这是为你生成的知识卡片..."），直接开始输出卡片。
- 不要编造原文没有的例子或数据。
- 不要把文章的每一段都机械转换成卡片——学会取舍。
- 不要用项目符号列表代替表格格式。
